## MODIFIED Requirements

### Requirement: Допустимые значения перечислимых полей

Hub SHALL ограничивать на уровне Postgres значения перечислимых текстовых колонок, на которые опираются
Literal-типы API и домена: `imports.source`, `imports.method`, `imports.mode`, `import_collections.kind`,
`albums.release_type`, `mix_settings.mode`, `mixes.mode`, `wave_sessions.mode`,
`favorite_subjects.target_type`. Наборы MUST совпадать с соответствующими Literal; изменение набора MUST
сопровождаться Alembic-миграцией. Ограничения MUST иметь имена `ck_<таблица>_<колонка>` и MAY допускать
`NULL` для nullable-полей.

Набор `CheckConstraint` в моделях и набор ограничений в схеме БД MUST совпадать: имя и выражение каждого
ограничения из `models.__table_args__` существуют в БД после `alembic upgrade head`, и ни одно `ck_*`
ограничение БД не отсутствует в моделях. Расхождение MUST обнаруживаться тестом, а не только `alembic check`.

#### Scenario: Допустимое значение
- **WHEN** приложение записывает значение из набора
- **THEN** запись сохраняется

#### Scenario: Недопустимое значение
- **WHEN** в колонку пытаются записать значение вне набора
- **THEN** Postgres отклоняет запись ошибкой ограничения
- **AND** строка не сохраняется

#### Scenario: Изменение набора
- **WHEN** набор допустимых значений меняется
- **THEN** change содержит Alembic-миграцию, обновляющую ограничение
- **AND** проверены `upgrade head` и откат

#### Scenario: Паритет с Literal
- **WHEN** выполняется тест паритета
- **THEN** каждое значение соответствующего Literal принимается БД
- **AND** заведомо чужое значение отвергается

#### Scenario: Расхождение модели и миграции
- **WHEN** `CheckConstraint` объявлен в модели, но не создан миграцией (или наоборот)
- **THEN** тест паритета моделей и миграций падает и называет таблицу и имя ограничения
