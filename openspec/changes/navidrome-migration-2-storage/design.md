## Context

См. `proposal.md — Why`. Сейчас `storage` работает с `Path`: `library/layout.py` строит пути, `importer.py` делает `os.replace`, `tagger.py` пишет теги на месте, `editor.py` перемещает файлы, `listen.py`/`light.py`/`probe.py` читают локальные файлы, `housekeeping.py` чистит `.trash`. После перехода на Postgres (этап 1) эти операции должны работать с объектным хранилищем.

## Goals / Non-Goals

**Goals:**
- Единый контракт хранения, не зависящий от ФС и S3-провайдера.
- Иммутабельные блобы, дедупликация, дешёвые правки метаданных.
- Предсказуемая согласованность «объект ↔ запись в БД» при сбоях.

**Non-Goals:**
- Не менять модель метаданных каталога (этап 3).
- Не менять API библиотеки для PWA (этап 6).
- Не реализовывать CDN и прямую раздачу клиентам.
- Не переносить существующие файлы (инстансов нет).

## Decisions

### 1. Шов `storage.backend`

Протокол: `put`, `get`, `get_range`, `head`, `delete`, `presign_get`, `list`. Реализации: `LocalBackend` (тесты/dev) и `S3Backend`. S3-клиент — `aioboto3`/`boto3` (presign), sync-часть выносится в `asyncio.to_thread`. Альтернатива — `s3fs`/FUSE отклонена: POSIX-семантика поверх S3 даёт скрытые блокировки и частичные записи.

### 2. Блобы и content addressing

Ключ объекта — `sha256` содержимого: `audio/<sha256>`, `covers/<sha256>`, `manifests/<sha256>/<uid>.json`. Хеш считается потоково по **исходным байтам** файла: импорт больше не вызывает `tagger.write_tags` и не меняет байты перед хешированием. Теги читаются при импорте и живут в БД/manifest; запись тегов в объект возможна только при экспорте/материализации (см. §9). Это обязательное условие дедупликации: иначе два одинаковых исходника с разными `uid` дали бы разные байты. Manifest — **на каждый трек**, потому что один блоб может обслуживать несколько треков; `blobs.manifest_key` хранит префикс/список. Таблица `blobs`:

| Поле | Смысл |
|---|---|
| `id` | внутренний ключ |
| `sha256` | уникальный адрес |
| `size`, `content_type` | параметры объекта |
| `status` | `pending` / `committed` / `deleted` |
| `created_at`, `committed_at`, `verified_at` | жизненный цикл |
| `manifest_prefix` | префикс `manifests/<sha256>/` |

`tracks.blob_id` и `albums.cover_blob_id` — внешние ключи. Дубликаты байтов не создают новый объект.

### 3. Двухфазная запись

1. Файл пишется в `staging`, считается `sha256` исходных байтов.
2. Объект загружается под временным ключом `pending/<uuid>` (единственная стратегия, без альтернативы `audio/<sha256>` с pending-статусом), идемпотентно.
3. Объект копируется/промоутится в `audio/<sha256>` и проверяется `head` (размер/хеш); только после этого в одной транзакции БД строка блоба становится `committed`. При сбое коммита остаётся `pending`-объект, ретрай идемпотентен по `sha256`.
4. GC раз в сутки листает бакет (`list`), вычитает `blobs.sha256` **по префиксу `audio/`** и удаляет остаток старше TTL; `pending/` чистится по TTL отдельно.
5. При повторной попытке тот же `sha256` не создаёт дубль.

Альтернатива — сначала БД, потом объект — даёт «битые» ссылки; отклонена.

### 4. Горячий кэш

Локальный каталог `DATA_DIR/cache/blobs/<sha256>` с LRU и лимитом (`STORAGE_CACHE_MAX_BYTES`). Чтение: cache hit → файл; miss → Range-проксирование из S3, а кэш заполняется в `<sha256>.part` с нулевого байта. Файл промоутится в `<sha256>` только когда `size == head`; частичный `.part` никогда не отдаётся как полный. Для ffprobe/ffmpeg и embedder — сначала докачать в кэш целиком. Single-flight по `sha256`, чтобы параллельные запросы не качали одно и то же. Растущие копии прослушивания живут отдельным не-блобовым namespace `DATA_DIR/cache/listen*` со своим LRU и Range-отдачей по мере роста, а не через `size == head`.

### 5. Стриминг

`listen.py` для библиотечных блобов: cache hit → `FileResponse`/Range; miss → Range-проксирование из S3 с заполнением кэша. Заголовки `Content-Length`, `Content-Range`, `Accept-Ranges`, `ETag` (sha256). `light.py` работает только с локальным кэшем.

### 6. Обложки

Обложки — отдельные блобы. Ресайз делается на лету и кэшируется локально по `(sha256, size)`. Если обложки нет, используется встроенная в аудио или заглушка, как сейчас.

### 7. Embedder

`library_items()` отдаёт `url` (presigned GET с TTL) вместо `path`. Если presign недоступен, используется Hub-endpoint `/api/media/blob/<sha256>`, защищённый `MEDIA_BLOB_TOKEN` (`Authorization: Bearer`, constant-time compare, `401` без токена); endpoint и его контракт описаны в спеке `storage`, а не только в design. Это сохраняет текущий контракт embedder (`url` уже поддержан).

### 8. Корзина, GC и бэкапы

Удаление — пометка `tracks.deleted_at` (и `blobs.status=deleted`, если нет других ссылок); восстановление в течение `trash_days` возвращает трек. После `trash_days` housekeeping удаляет саму строку трека (ссылка исчезает), затем GC удаляет блоб; `pending` — после TTL, а также объекты, которых нет в БД (листинг бакета). Версионирование бакета включается в конфиге и используется как дополнительная страховка. Бэкап БД — `pg_dump`; бакет — версии/репликация, без файлового rsync.

### 9. Теги

`tagger.py` больше не пишет теги «на месте» и **не вызывается в пути импорта**: теги читаются и хранятся в БД/manifest. Запись тегов в объект возможна только через временную копию и пере-загрузку в операции экспорта/материализации, не в обычной правке. Это же условие делает `sha256` стабильным и дедупликацию возможной. Правка/перемещение/удаление трека — только метаданные БД и логический путь; удаление — `tracks.deleted_at`; обложка — блоб `covers/<sha256>`. MODIFIED-дельты `library` («Правка альбома и треков», «Обложки альбомов») делает этап 3; здесь фиксируются только задачи storage, чтобы не дублировать capability.

### 10. Логический путь

`tracks.path` и `albums.cover_path` остаются в БД как логический путь для отображения/экспорта и очищаются тем же `layout.sanitize_component`. Они больше не уникальны для блоба: при дедупликации два трека могут делить `blob_id`, но иметь разные логические пути; уникальность `tracks.path` сохраняется только в пределах логической библиотеки и проверяется при импорте.

## Risks / Trade-offs

- [Латентность S3 на первом байте] → cache-first, Range-прокси, single-flight; замер на RustFS.
- [Утечка `pending`-объектов] → GC по TTL + метрика количества.
- [Presigned URL утекает в логи] → короткий TTL, не логировать URL, использовать Hub-endpoint как fallback.
- [Стоимость хеширования больших FLAC] → потоковый хеш при копировании в staging, без повторного чтения.
- [Неполная совместимость RustFS] → smoke на Range, multipart, conditional GET; абстракция позволяет заменить провайдера.
- [Правки метаданных расходятся с manifest] → manifest обновляется фоновой задачей; источник истины — БД.
- [Хеш считается после тегирования] → импорт не вызывает `write_tags`; тест «два импорта одного файла → один блоб».
- [Сбой до создания строки блоба] → `pending/<uuid>` + суточный листинг бакета и вычитание `blobs.sha256`.
- [Trash без схемы] → `tracks.deleted_at` + restore-сценарий и endpoint.
- [Частичный кэш отдаётся как полный] → `.part` + промоушен по `size == head`.
- [S3 API не стандартизует versioning/quota] → capability-checklist в задаче 1.2, quota настраивается явно или сценарий убирается.
- [Manifest на блоб не восстанавливает все треки] → manifest на каждый `uid` и сценарий «делимый блоб».

## Migration Plan

1. Добавить `blobs`, ссылки, `tracks.deleted_at`, логические пути в миграции Postgres.
2. Реализовать `storage.backend` с локальным и S3-бэкендами; проверить capabilities RustFS.
3. Перевести запись (импорт, uploads, editor) на блобы без `write_tags`.
4. Перевести чтение (stream, probe, light, covers) на кэш.
5. Перевести embedder на URL и добавить blob-endpoint.
6. Включить GC (включая листинг), корзину/restore, health и бэкапы.
7. Добавить экспорт/материализацию с записью тегов.
8. Прогнать тесты и smoke на RustFS.

Откат: `LocalBackend` — dev/test-only, не production-режим; рабочий откат — восстановить БД и бакет из версии/дампа, вернуть предыдущий код. Данные в S3 остаются.
