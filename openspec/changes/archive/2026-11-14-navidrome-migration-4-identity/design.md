## Context

См. `proposal.md — Why`. Сейчас `auth.py` проверяет пару через Navidrome (`ping`/`getUser`), `accounts.py` создаёт пользователя через `NavidromeAdmin`, пароль хранится в `nd_password_enc`, а Google-вход возвращает пароль Navidrome для плеера. После этапа 1 есть Postgres; после этапа 3 — каталог. Рабочих инстансов нет.

## Goals / Non-Goals

**Goals:**
- Локальные учётки и токены, не зависящие от ND.
- Безопасный bootstrap администратора.
- Готовность к внешнему OIDC-входу без превращения Hub в OIDC Provider.

**Non-Goals:**
- Не реализовывать OIDC Provider (`/authorize`, `/token`, JWKS для третьих сторон).
- Не добавлять MFA и восстановление по коду (отдельные change’и).
- Не менять cookie-контракт PWA сверх необходимого.
- Не проектировать мобильные клиенты.

## Decisions

### 1. Хеширование паролей

argon2id (`argon2-cffi`) с параметрами по умолчанию библиотеки. Альтернатива bcrypt отклонена из-за лимита 72 байта и меньшей устойчивости к GPU. Хеш — единственное, что хранится; пароль не логируется и не возвращается API.

### 2. Токены

- Access — JWT, TTL 15 минут, подпись ключом `JWT_SIGNING_KEY` (EdDSA или HS256; выбор фиксируется в конфиге). В токене: `sub` (uid пользователя), `iat`, `exp`, `jti`, `role`.
- Refresh — случайный opaque-токен, TTL 30 дней, хранится как SHA-256 в `refresh_tokens` с `family_id`, `device_id`, `revoked_at`; ответ ротации сохраняется в `replacement_enc` (Fernet), чтобы повтор в окне идемпотентности вернул ту же пару без выпуска второго токена. `device_id` — серверный HttpOnly cookie `hm_device`, сравнивается с полем записи. Окно N = 10 с (конфиг).
- Ротация при каждом refresh. Все операции над строками сессии блокируют их в порядке `id` (`SELECT … FOR UPDATE`
  с `ORDER BY id`), поэтому одновременный refresh, устаревший replay и logout/смена пароля сериализуются и не дают
  взаимоблокировок; второй одновременный refresh получает сохранённую пару, а не вторую живую. Строки с истёкшим
  сроком удаляет ежедневный housekeeping, а не путь запроса. Повторное использование старого токена вне окна
  отзывает всю семью; в окне с тем же `device_id` возвращается сохранённый `replacement_enc`. `replacement_enc` очищается при следующей ротации, отзыве семьи/устройства и logout; нерасшифровываемое значение
(смена `HUB_SECRET_KEY`) даёт `401` без отзыва семьи.
- Таблица `sessions` заменяется `refresh_tokens`; `last_seen_at` пишется при refresh/access. Добавляются `GET /api/auth/sessions` и `DELETE /api/auth/sessions/{id}` для списка/отзыва устройств.
- Access JWT проверяется по подписи и `exp`; отзыв access до `exp` не гарантируется (TTL ≤ 15 минут), отзыв устройства действует на refresh.
- Транспорт для PWA: access в HttpOnly `hm_session`, refresh в HttpOnly `hm_refresh` (path `/api/auth`), `Secure` при HTTPS, `SameSite=Lax`.
- Альтернатива — только opaque-сессии (как сейчас) — отклонена: не готовит почву под мобильные клиенты и OIDC.

### 3. Bootstrap администратора

Источники: `ADMIN_USERNAME` + `ADMIN_PASSWORD` (или `ADMIN_PASSWORD_HASH`) либо одноразовый `ADMIN_BOOTSTRAP_TOKEN` через `POST /api/auth/bootstrap`. Создание идемпотентно: если админ уже есть, ничего не происходит. Дефолтных `admin/admin` нет. Одноразовость токена обеспечивается singleton-строкой `bootstrap_state` (`bootstrap_consumed_at`) и лимитером неверных попыток (таблица `login_attempts`); повторный вызов — `409`; `ADMIN_PASSWORD_HASH` не проходит проверку политики (хеш уже вычислен). Пароль проверяется по политике; флаг `must_change_password` заставляет сменить пароль при первом входе и блокирует остальные действия до смены. Восстановление при блокировке — CLI-команда сброса (документируется).

`must_change_password` выставляется путём одноразового токена и CLI-сбросом; пароль, заданный оператором через
`ADMIN_PASSWORD`/`ADMIN_PASSWORD_HASH`, считается выбранным осознанно и смены не требует.

### 4. OIDC как Relying Party

Провайдеры описываются конфигом: `issuer`, `client_id`, `client_secret` (шифруется Fernet), `scopes`, `enabled`. Google — встроенный провайдер через discovery. Поток — Authorization Code + PKCE, `state` и `nonce` обязательны. Связь хранится в `oauth_links(provider, issuer, subject, user_id)` с уникальностью `(issuer, subject)`.

Правила привязки:
- Автоматическая привязка по email MUST NOT выполняться (защита от захвата аккаунта).
- Непривязанный вход без инвайта → `409`; с действующим инвайтом → создаётся локальный пользователь и связь.
- Конфликт `(issuer, subject)` → `409`.
- Отвязка разрешена, если остаётся пароль или другая связь.
- Discovery/`state`/`nonce`/PKCE ошибки и недоступный провайдер возвращают `400`/`502` с русским сообщением, без создания сессии.

### 5. Регистрация

Инвайты и email-коды создают локального пользователя. Создание пользователя в Navidrome удаляется. Приглашения остаются одноразовыми и сроками. **Переходный период:** пока PWA читает `/api/nd/*` до этапа 6, `/api/nd/*` для пользователя без `nd_username` отдаёт ND-совместимую форму из Hub-каталога `/api/library/*` (доступен после этапа 3), а не `409`; `user_navidrome` MUST NOT вызываться без кредов; это фиксируется в рисках и проверке, а не молчаливой поломкой.

### 6. Админ-доступ

`is_admin` хранится в Hub. Список пользователей — локальный; `last_seen_at` обновляется по `refresh_tokens`/access; счётчики ♥/плейлистов берутся из Hub (после этапа 5) или показываются пустыми. Пользователи ND в списке отсутствуют.

### 7. Ошибки и лимиты

`401` — неверные данные/истёкший токен; `403` — не админ/требуется смена пароля (кроме login, refresh, logout, `GET /api/auth/me`, `POST /api/auth/password`); `409` — занятое имя/конфликт привязки; `429` — лимит попыток/refresh. Формат — `{"detail": "<русское сообщение>"}`. Лимиты локальные, без оглядки на Subsonic-бюджет ND. Лимитер хранится в Postgres (таблица попыток), чтобы переживать рестарт и быть общим для воркеров; in-process-словарь не используется.

### 8. Ключи и секреты

`session_days` из конфига выводится из обращения: access TTL 15 минут, refresh 30 дней; ключ переименовывается/удаляется с миграционной заметкой. `JWT_SIGNING_KEY` и `HUB_SECRET_KEY` — обязательные переменные; без них Hub не стартует в небезопасном режиме. OIDC-секреты шифруются Fernet. Ротация ключей JWT — отдельный change (пока фиксируется `kid` в заголовке).

### 9. Смена пароля

Добавляется `POST /api/auth/password` (текущий + новый пароль), `MeOut.must_change_password` и `403` на остальные действия до смены. Успешная смена отзывает все refresh-семьи, кроме текущей, и логирует событие без пароля. Для OIDC-only аккаунта текущий пароль не требуется (пароля нет). CLI-сброс делает то же и выставляет `must_change_password`.

## Risks / Trade-offs

- [Кража refresh-токена] → rotation + reuse detection + HttpOnly/Secure; журнал отзыва.
- [Захват аккаунта через OIDC по email] → запрет автопривязки, только явная линковка.
- [Блокировка админа] → CLI-сброс и документированный recovery; bootstrap идемпотентен.
- [Потеря cookie-совместимости PWA] → имя `hm_session` сохраняется; контрактные тесты PWA.
- [Расхождение `role` в JWT и БД] → `role` проверяется по БД для админских endpoint'ов, JWT — только для идентификации.
- [Смена `HUB_SECRET_KEY`] → OIDC-секреты перестают расшифровываться; документированная процедура ротации.
- [Параллельный refresh разлогинивает] → окно идемпотентности для того же `device_id`.
- [Нет endpoint смены пароля] → отдельное требование и `must_change_password` в `MeOut`.
- [ND-креды удалены раньше 7] → оставить `nd_username`/`nd_password_enc` nullable, не писать `nd_password_enc`, drop — только этап 7.
- [Лимитер теряется при рестарте] → хранение попыток в Postgres.
- [Stage 4 ломает ND-функции до 6] → документированный `409`/деградация и проверка на пользователе без ND-учётки.
- [Одноразовый bootstrap-токен из env] → `bootstrap_consumed_at` + лимитер + endpoint.

## Migration Plan

1. Добавить поля `users.username`, `password_hash`, `must_change_password`; таблицы `refresh_tokens`, `oauth_links`, `login_attempts`; **не удалять** `nd_username`/`nd_password_enc` — оставить nullable, перестать писать `nd_password_enc`; drop — этап 7.
2. Реализовать argon2-вход, bootstrap, смену пароля и refresh-ротацию.
3. Перевести регистрацию и email на локальных пользователей.
4. Перевести Google на OIDC RP и добавить generic-провайдеров.
5. Обновить админский список.
6. Прогнать тесты входа, refresh, отзыва, линковки, bootstrap и смены пароля.

Откат: вернуть прежнюю схему аутентификации из git; данных ND нет, потери пользователей не будет при пустой БД.
