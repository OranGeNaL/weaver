## Context

См. `proposal.md — Why`. Анализатор pi-lens запускает Pyright по `hub/app` и показывает ~50 ошибок в ~25
модулях. Это не следствие одного изменения: ошибки копятся с момента появления интеграций (OpenAI-клиент,
`httpx`/`httpx2`, Pydantic-схемы с `Literal`, SQLAlchemy 2.1). Поведение системы при этом корректно.

## Goals / Non-Goals

**Goals:**
- Воспроизводимая проверка типов: закреплённый анализатор + конфиг в репозитории.
- Ноль ошибок типизации в `hub/app` без изменения поведения и API.
- Правило для будущего кода: новый долг не появляется.

**Non-Goals:**
- Не вводить `mypy` параллельно с Pyright.
- Не включать `strict` целиком: цель — убрать реальные ошибки, а не переписать модель типов.
- Не менять схему БД, API, очереди и клиентские контракты.
- Не типизировать сторонние библиотеки и не писать стабы.

## Decisions

### 1. Инструмент и профиль

Pyright (тот же анализатор, что использует pi-lens), версия закрепляется dev-зависимостью, конфиг —
`hub/pyrightconfig.json` с `include: ["app"]` и `typeCheckingMode: "standard"`. `standard`, а не `strict`:
`strict` требует доменных протоколов для каждого словаря состояния (`wave`, `smart`, taste-математика) и меняет
объём работ на порядок.

### 2. Политика исправлений

- Сначала сужение типов проверками (`if x is None: continue`, `isinstance`, `Literal`-приведение на границе API).
- Где тип гарантирован инвариантом — `cast` с комментарием, объясняющим инвариант.
- `# type: ignore[код]` — только если ошибка ложная, с указанием кода и причины.
- Никаких изменений логики, сигнатур публичных функций и форматов ответов.

### 3. Порядок

Группами по доменам (см. `tasks.md`): инфраструктура и конфиг → модели и доступ к данным → API → фоновые
задачи → импорт/каталог → рекомендации/аналитика → ассистент → финальная проверка. Каждая группа —
самостоятельный коммит с зелёным `ruff` и без роста ошибок Pyright.

### 4. Проверка в наборе обязательных

Команда проверки типов добавляется рядом с `ruff` в документацию и в задачи проверки change'ей. Порог — ноль
ошибок; предупреждения не блокируют.

## Risks / Trade-offs

- [`cast` скрывает реальную ошибку] → комментарий с инвариантом и, где возможно, runtime-проверка.
- [Правки типизации задевают поведение] → только сужения и аннотации; поведение подтверждается тестами Hub.
- [Версия Pyright меняет набор ошибок] → версия закреплена, обновление — отдельным шагом с полным прогоном.
- [Долг возвращается] → проверка типов в обязательном наборе и в задачах новых change'ей.

## Migration Plan

1. Добавить dev-зависимость и `pyrightconfig.json`.
2. Зафиксировать текущий список ошибок как базовый (в tasks.md по группам).
3. Исправлять группами, сверяя отсутствие поведенческих изменений (`pytest`).
4. Включить проверку в документацию проверок (`hub/API.md`/`README` — где описан набор).

Откат: удалить конфиг и зависимость; правки типизации безопасны по отдельности.
