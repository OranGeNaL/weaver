## Purpose

Домен описывает локальные учётные записи Hub, вход по паролю (argon2id), сессии и токены (access JWT и rotating refresh), смену пароля, bootstrap администратора, регистрацию по приглашению и email, вход через внешние OIDC-провайдеры (включая Google), административный доступ и защиту учётных данных. Источник истины для пользователей и паролей — Hub; внешнего медиасервера в системе нет.

## Requirements

### Requirement: Вход по локальной учётной записи

Hub SHALL проверять логин и пароль по локальной учётной записи Hub (argon2id) и создавать сессию только после успешной проверки. Пользователь MUST иметь возможность войти по имени или по подтверждённому email, связанному с аккаунтом.

#### Scenario: Успешный вход
- **WHEN** пользователь отправляет корректные `username` и `password` в `POST /api/auth/login`
- **THEN** Hub проверяет хеш пароля, обновляет `last_seen_at` существующего пользователя и устанавливает HttpOnly cookie `hm_session`
- **AND** ответ содержит `MeOut` с именем, признаком администратора и публичными URL

#### Scenario: Неверный пароль
- **WHEN** пользователь отправляет неверный пароль
- **THEN** Hub возвращает `401` с русским сообщением
- **AND** сессия не создаётся

#### Scenario: Вход по email
- **WHEN** пользователь вводит email, подтверждённый за аккаунтом
- **THEN** Hub разрешает вход по этому email и возвращает имя пользователя в `MeOut.username`

#### Scenario: Начальный пароль
- **WHEN** пользователь входит с паролем, выданным bootstrap-токеном или сбросом через CLI
- **THEN** Hub требует смену пароля перед остальными действиями

### Requirement: Сессии и токены

Hub SHALL выдавать короткоживущий access JWT и rotating refresh-токен. Access-токен MUST передаваться в HttpOnly cookie `hm_session`, refresh-токен — в HttpOnly cookie `hm_refresh` с путём `/api/auth`. Refresh-токен MUST храниться в БД как хеш; ответ ротации MUST сохраняться в `replacement_enc` (Fernet) для идемпотентного повтора, `device_id` — в HttpOnly cookie `hm_device`. Выход и отзыв MUST делать refresh недействительным. Таблица `sessions` заменяется `refresh_tokens`; `last_seen_at` обновляется при refresh/access. Для списка устройств Hub SHALL отдавать `GET /api/auth/sessions` и `DELETE /api/auth/sessions/{id}`, где `{id}` — `family_id`/устройство.

#### Scenario: Доступ к защищённому endpoint
- **WHEN** запрос приходит с действующим access JWT
- **THEN** Hub определяет пользователя и разрешает доступ к endpoint'у

#### Scenario: Истёкший access
- **WHEN** access JWT истёк, а refresh-токен действует
- **THEN** клиент вызывает `POST /api/auth/refresh`
- **AND** Hub выдаёт новый access и ротирует refresh

#### Scenario: Повторное использование refresh
- **WHEN** предъявлен уже ротированный refresh-токен вне окна идемпотентности
- **THEN** Hub отзывает всю цепочку сессии
- **AND** возвращает `401`

#### Scenario: Параллельный refresh
- **WHEN** два запроса с тем же `hm_device` приходят в окне идемпотентности, а семья не отозвана
- **THEN** Hub возвращает сохранённую в `replacement_enc` пару
- **AND** не выпускает второй токен и не разлогинивает устройство

#### Scenario: Выход
- **WHEN** пользователь вызывает `POST /api/auth/logout`
- **THEN** Hub отзывает семью refresh-токенов устройства и очищает cookie
- **AND** отвечает `{"ok": true}`

#### Scenario: Истёкшая сессия
- **WHEN** cookie отсутствует, access и refresh истекли или отозваны
- **THEN** Hub возвращает `401` с сообщением о необходимости входа

#### Scenario: Отзыв устройства
- **WHEN** пользователь отзывает устройство в списке сессий
- **THEN** все refresh-токены семьи этого устройства перестают действовать

#### Scenario: Список сессий
- **WHEN** пользователь вызывает `GET /api/auth/sessions`
- **THEN** Hub возвращает устройства, время последнего использования и текущее устройство
- **AND** не раскрывает сами токены

### Requirement: Регистрация по приглашению

Hub SHALL создавать нового локального пользователя Hub по одноразовому коду приглашения. Код MUST быть нормализован, одноразовым и ограниченным сроком действия.

#### Scenario: Успешная регистрация по коду
- **WHEN** пользователь отправляет действующий код, свободное имя и корректный пароль в `POST /api/auth/register`
- **THEN** Hub создаёт локального пользователя Hub и сессию
- **AND** приглашение помечается использованным

#### Scenario: Использованный или истёкший код
- **WHEN** код уже использован или истёк
- **THEN** Hub возвращает `400` и не создаёт пользователя

#### Scenario: Занятое имя
- **WHEN** запрошенное имя уже занято
- **THEN** Hub возвращает `409`

### Requirement: Регистрация по email

Hub SHALL отправлять шестизначный код на email через SMTP и создавать аккаунт только после проверки последнего кода. Hub MUST ограничивать повторную отправку, количество писем и число неверных попыток.

#### Scenario: Отправка кода
- **WHEN** пользователь запрашивает код для корректного email без аккаунта
- **THEN** Hub создаёт код, отправляет письмо и возвращает `resend_in`
- **AND** предыдущие коды этого адреса перестают быть действующими

#### Scenario: Регистрация по коду
- **WHEN** пользователь отправляет последний действующий код, имя и пароль в `POST /api/auth/email/register`
- **THEN** Hub создаёт локального пользователя Hub и сессию

#### Scenario: Слишком частая отправка
- **WHEN** новый код запрашивают раньше `resend_in` или исчерпан часовой лимит на адрес
- **THEN** Hub возвращает `429` с указанием ограничения

#### Scenario: Исчерпан суточный лимит писем
- **WHEN** сервер уже отправил `EMAIL_DAILY_LIMIT` писем за 24 часа
- **THEN** Hub возвращает `503` с предложением попробовать завтра

#### Scenario: Неверный код
- **WHEN** пользователь вводит неверный код
- **THEN** Hub уменьшает число оставшихся попыток и возвращает `400`
- **AND** после исчерпания попыток код перестаёт действовать

### Requirement: Вход через OIDC и привязка аккаунта

Hub SHALL поддерживать вход через внешних OIDC-провайдеров (Google и generic) и MUST связывать пару `iss` + `sub` с локальной учётной записью. Hub MUST NOT автоматически связывать OIDC-аккаунт по email и MUST NOT быть OIDC Provider для сторонних приложений.

#### Scenario: Вход в связанный аккаунт
- **WHEN** пользователь завершает OIDC-вход аккаунтом, уже связанным с пользователем Hub
- **THEN** Hub создаёт сессию и возвращает `MeOut`

#### Scenario: Непривязанный аккаунт без приглашения
- **WHEN** OIDC-аккаунт не связан и код приглашения не передан
- **THEN** Hub возвращает `409`

#### Scenario: OIDC с приглашением
- **WHEN** OIDC-аккаунт не связан, но передан действующий код приглашения
- **THEN** Hub создаёт локального пользователя и связь `iss`+`sub`
- **AND** приглашение помечается использованным

#### Scenario: Ошибка state или nonce
- **WHEN** `state`/`nonce` не совпадают или истекли
- **THEN** Hub возвращает `400` и не создаёт сессию

#### Scenario: Discovery недоступен
- **WHEN** OIDC-провайдер не отвечает на discovery
- **THEN** Hub возвращает `502` с русским сообщением

#### Scenario: Привязка OIDC
- **WHEN** авторизованный пользователь завершает OIDC-вход в `POST /api/auth/oidc/link/{provider}`
- **THEN** Hub связывает `iss` + `sub` и возвращает обновлённый `MeOut`

#### Scenario: Отвязка OIDC
- **WHEN** пользователь вызывает `DELETE /api/auth/oidc/link/{provider}`
- **THEN** Hub удаляет связь, если у аккаунта остаётся пароль или другой способ входа

#### Scenario: Привязка Google
- **WHEN** авторизованный пользователь завершает Google-вход в `POST /api/auth/oidc/link/google`
- **THEN** Hub связывает `iss` + `sub` и возвращает обновлённый `MeOut`

#### Scenario: Отвязка Google
- **WHEN** пользователь вызывает `DELETE /api/auth/oidc/link/google`
- **THEN** Hub удаляет связь, если у аккаунта остаётся пароль или другой способ входа

#### Scenario: Конфликт привязки
- **WHEN** `iss` + `sub` уже связан с другим пользователем
- **THEN** Hub возвращает `409` и не перезаписывает связь

### Requirement: Ограничение попыток входа

Hub SHALL ограничивать число неудачных попыток входа по локальной учётной записи, чтобы защитить от перебора.

#### Scenario: Превышение лимита попыток
- **WHEN** для одного имени за короткое окно превышено допустимое число неудачных попыток
- **THEN** Hub возвращает `429` с `Retry-After`
- **AND** не проверяет пароль до окончания окна

### Requirement: Административный доступ

Hub SHALL разрешать административные endpoint'ы только пользователям с `is_admin`. Администратор MUST видеть пользователей, расходы AI, загрузки, загруженные треки, ♥ и плейлисты, а также управлять приглашениями.

#### Scenario: Администратор открывает список пользователей
- **WHEN** администратор вызывает `GET /api/admin/users`
- **THEN** Hub возвращает локальных пользователей и агрегаты по Hub
- **AND** `last_seen_at` берётся из `refresh_tokens`/access

#### Scenario: Неадминистратор
- **WHEN** обычный пользователь вызывает административный endpoint
- **THEN** Hub возвращает `403`

#### Scenario: Создание приглашения
- **WHEN** администратор вызывает `POST /api/admin/invites`
- **THEN** Hub создаёт код с заданным сроком и возвращает его в формате «ABCD-EFGH»

### Requirement: Защита секретов

Hub SHALL хранить пароли только как argon2id-хеши, подписывать JWT ключом из окружения и MUST NOT логировать пароли, cookie, токены, OIDC-секреты и содержимое `.env`.

#### Scenario: Сохранение пароля
- **WHEN** пользователь регистрируется или меняет пароль
- **THEN** в БД сохраняется только argon2id-хеш
- **AND** исходный пароль не сохраняется и не логируется

#### Scenario: Ключ подписи JWT
- **WHEN** Hub выдаёт токен
- **THEN** используется ключ из окружения
- **AND** при его отсутствии Hub не стартует с небезопасным дефолтом

#### Scenario: Ошибка расшифровки
- **WHEN** `HUB_SECRET_KEY` изменён и сохранённый OIDC-секрет нельзя расшифровать
- **THEN** Hub возвращает ошибку без вывода секрета в лог

### Requirement: Смена пароля

Hub SHALL предоставлять `POST /api/auth/password` для смены пароля по текущему паролю и MUST отдавать `must_change_password` в `MeOut`. До смены пароля остальные действия MUST возвращать `403`, кроме login, refresh, logout, `GET /api/auth/me` и `POST /api/auth/password`.

#### Scenario: Успешная смена
- **WHEN** пользователь отправляет текущий и новый корректный пароль (для OIDC-only аккаунта текущий не требуется)
- **THEN** Hub сохраняет новый argon2id-хеш
- **AND** отзывает остальные refresh-семьи, кроме текущей

#### Scenario: Неверный текущий пароль
- **WHEN** текущий пароль неверен
- **THEN** Hub возвращает `401` и не меняет пароль

#### Scenario: Обязательная смена
- **WHEN** `must_change_password` установлен
- **THEN** `MeOut` содержит флаг
- **AND** остальные действия возвращают `403`, кроме login, refresh, logout, `GET /api/auth/me` и `POST /api/auth/password`

### Requirement: Bootstrap администратора

Hub SHALL создавать первого администратора при первом старте без дефолтных учётных данных. Источник — переменные окружения или одноразовый bootstrap-токен; операция MUST быть идемпотентной. Пароль, заданный оператором через `ADMIN_PASSWORD`/`ADMIN_PASSWORD_HASH`, считается осознанным выбором и принудительной смены не требует.

#### Scenario: Первый старт с окружением
- **WHEN** БД пуста и заданы `ADMIN_USERNAME` и `ADMIN_PASSWORD` (или `ADMIN_PASSWORD_HASH`)
- **THEN** Hub создаёт администратора с argon2id-хешем
- **AND** повторный старт не создаёт второго администратора

#### Scenario: Bootstrap-токен
- **WHEN** задан одноразовый `ADMIN_BOOTSTRAP_TOKEN` и вызван `POST /api/auth/bootstrap`
- **THEN** Hub создаёт администратора и сохраняет `bootstrap_consumed_at`
- **AND** повторный вызов отклоняется (`409`), а неверные токены ограничиваются лимитером попыток

#### Scenario: Слабый пароль
- **WHEN** bootstrap-пароль не проходит политику
- **THEN** Hub не создаёт администратора
- **AND** пишет понятную ошибку

#### Scenario: Нет данных для bootstrap
- **WHEN** БД пуста и данные администратора не заданы
- **THEN** Hub не создаёт `admin/admin`
- **AND** логирует инструкцию, как создать администратора

#### Scenario: Смена начального пароля
- **WHEN** администратор входит с паролем, выданным bootstrap-токеном или сбросом через CLI
- **THEN** Hub требует сменить пароль
- **AND** до смены остальные действия недоступны
