## Purpose

Домен описывает физическое хранение медиафайлов: раскладку `MUSIC_ROOT`, безопасные пути, staging, корзину, атомарные перемещения, проверку файлов и временные копии для прослушивания. Домен не владеет метаданными альбомов и треков и не обращается к внешнему медиасерверу.

## Requirements

### Requirement: Раскладка библиотеки

Hub SHALL хранить **логический** путь трека в БД по схеме `{AlbumArtist}/{Year - Album}/{Disc}-{NN} - {Title}.{ext}` и MUST очищать компоненты тем же `layout.sanitize_component` (недопустимые символы, пробелы, зарезервированные имена). Физический объект адресуется `sha256`; логический путь используется для отображения и экспорта/материализации, а не как источник истины.

#### Scenario: Новый трек альбома
- **WHEN** файл импортируется в альбом с исполнителем, годом, номером диска и трека
- **THEN** в БД сохраняется предсказуемый логический путь
- **AND** объект в S3 адресуется по `sha256`
- **AND** кириллица и Unicode сохраняются в логическом пути

#### Scenario: Неизвестный год
- **WHEN** у альбома нет года
- **THEN** логический каталог альбома называется только по названию альбома

#### Scenario: Логический путь
- **WHEN** трек импортируется
- **THEN** в БД сохраняется очищенный логический путь
- **AND** объект в S3 адресуется по `sha256`

#### Scenario: Опасное имя
- **WHEN** название содержит `..`, `/`, `\`, управляющие символы или зарезервированное имя вроде `CON`
- **THEN** логический путь очищается и не выходит за пределы библиотеки

### Requirement: Staging загрузок и импорта

Hub SHALL использовать локальный `MUSIC_ROOT/staging` для временных файлов загрузок, скачиваний и подготовки объектов S3. Каталог элемента загрузки MUST удаляться в `finally` при завершении задачи; ежедневная очистка MUST покрывать только `staging/uploads`. Каталоги `staging/dl/*`, оставшиеся после аварийного завершения контейнера, автоматически не очищаются.

#### Scenario: Скачивание трека
- **WHEN** запущена загрузка трека
- **THEN** файл сохраняется в отдельный staging-каталог элемента
- **AND** после загрузки в S3 каталог удаляется в `finally`

#### Scenario: Аварийное завершение
- **WHEN** контейнер завершился во время загрузки
- **THEN** каталог `staging/dl/<item_id>` MAY остаться до ручной очистки

#### Scenario: Загрузка своего файла
- **WHEN** пользователь загружает файл через `/api/uploads`
- **THEN** файл сохраняется в `staging/uploads/<user_id>/`
- **AND** при отмене или ошибке временный файл удаляется

#### Scenario: Устаревшие uploads
- **WHEN** файл uploads остаётся в staging дольше установленного срока
- **THEN** ежедневный housekeeping удаляет его

### Requirement: Корзина и срок хранения

Hub SHALL помечать удалённые треки через `tracks.deleted_at` и сохранять возможность восстановления в течение `library.trash_days`. По истечении срока строка трека MUST удаляться (ссылка исчезает), после чего блоб MUST удаляться из S3, если у него не осталось других ссылок; версионирование бакета MAY использоваться для дополнительного восстановления.

#### Scenario: Удаление трека
- **WHEN** пользователь удаляет трек
- **THEN** у трека выставляется `deleted_at`
- **AND** блоб не удаляется сразу

#### Scenario: Восстановление
- **WHEN** пользователь восстанавливает трек в течение `trash_days`
- **THEN** `deleted_at` снимается
- **AND** блоб остаётся доступным

#### Scenario: Очистка корзины
- **WHEN** трек находится в корзине дольше `trash_days`
- **THEN** housekeeping удаляет строку трека
- **AND** затем GC удаляет блоб из S3, если нет других ссылок

### Requirement: Проверка медиафайла

Hub SHALL пытаться прочитать аудиофайл через ffprobe, используя локальный кэш или временную копию из S3, и MUST сохранять длительность, битрейт и кодек, когда проверка удалась. Для скачанных файлов неудачная проверка или несовпадение длительности MUST отклонять кандидата; для загруженных пользователем файлов ошибка ffprobe MUST логироваться, но импорт MAY продолжаться без этих полей.

#### Scenario: Корректный файл
- **WHEN** ffprobe читает аудиофайл из кэша или временной копии
- **THEN** Hub сохраняет длительность, битрейт и кодек
- **AND** файл допускается к импорту

#### Scenario: Повреждённый файл при скачивании
- **WHEN** postcheck не может прочитать скачанный файл или длительность не совпадает
- **THEN** кандидат отклоняется
- **AND** временный файл удаляется

#### Scenario: Ошибка ffprobe при загрузке пользователем
- **WHEN** ffprobe не может прочитать загруженный файл
- **THEN** Hub логирует предупреждение
- **AND** импортирует файл без длительности, битрейта и кодека

#### Scenario: Подозрительная тишина
- **WHEN** postcheck находит длинную тишину
- **THEN** трек импортируется с предупреждением

### Requirement: Временные копии для прослушивания

Hub SHALL хранить серверные копии файлов для `listen` и лёгкие Opus-копии в локальном hot-cache с лимитом размера и вытеснением по давности. Копии MUST NOT попадать в S3. Растущие копии прослушивания MUST жить в отдельном namespace `cache/listen*` и отдаваться по Range по мере роста, не дожидаясь полного размера.

#### Scenario: Поток из YouTube
- **WHEN** googlevideo-файл нельзя отдать напрямую
- **THEN** Hub скачивает серверную копию в локальный кэш
- **AND** отдаёт клиенту Range-запросы по мере роста копии

#### Scenario: Лёгкий вариант
- **WHEN** клиент запрашивает `q=mobile` для тяжёлого файла
- **THEN** Hub отдаёт Opus-копию из локального кэша, если она готова
- **AND** иначе отдаёт оригинал с заголовком `X-HomeMusic-Variant: original-pending`

#### Scenario: Переполнение кэша
- **WHEN** суммарный размер копий превышает лимит
- **THEN** Hub удаляет копии, которые дольше всего не использовались

### Requirement: Отчёт о свободном месте

Hub SHALL сохранять `free_bytes` в статистике импорта, определяя его как свободное место локального кэша/staging, и MAY добавлять `bucket_bytes`/`bucket_quota` при наличии. Автоматической блокировки операций по свободному месту нет.

#### Scenario: Предпросмотр импорта
- **WHEN** пользователь открывает предпросмотр импорта
- **THEN** Hub возвращает `free_bytes` для локального кэша/staging
- **AND** клиент MAY показать предупреждение о нехватке места

#### Scenario: Внешний S3
- **WHEN** провайдер не сообщает квоту
- **THEN** Hub возвращает `bucket_bytes` без `bucket_quota`
- **AND** не блокирует импорт

### Requirement: S3 как primary-хранилище

Hub SHALL хранить аудио и обложки библиотеки в S3-совместимом хранилище. Локальный диск MUST использоваться только для staging, hot-cache и временных файлов ffmpeg/ffprobe. Доступ MUST задаваться через конфигурацию `endpoint`, `bucket`, `region`, `access key`, `secret key` и `path-style`.

#### Scenario: Запись трека
- **WHEN** трек импортируется в библиотеку
- **THEN** аудио-байты сохраняются в бакет S3
- **AND** в локальной библиотеке не остаётся постоянной копии

#### Scenario: Внешний S3
- **WHEN** конфигурация указывает внешний S3 endpoint
- **THEN** Hub работает без локального RustFS
- **AND** поведение не зависит от конкретного S3-провайдера

#### Scenario: fs в production
- **WHEN** `STORAGE_BACKEND=fs` в production
- **THEN** Hub отказывается стартовать

#### Scenario: S3 недоступен
- **WHEN** бакет недоступен на старте
- **THEN** health сообщает деградацию хранилища
- **AND** операции, требующие байтов, возвращают понятную ошибку

### Requirement: Иммутабельные блобы и дедупликация

Hub SHALL хранить аудио как иммутабельные блобы, адресуемые по `sha256` содержимого. Метаданные трека (название, исполнитель, альбом, теги, `uid`) MUST храниться в БД. Один блоб MAY обслуживать несколько треков.

#### Scenario: Повторяющиеся байты
- **WHEN** в библиотеку импортируются два трека с одинаковыми аудио-байтами
- **THEN** создаётся один блоб
- **AND** два трека ссылаются на него

#### Scenario: Правка метаданных
- **WHEN** пользователь меняет название или исполнителя трека
- **THEN** обновляется только запись в БД
- **AND** аудио-блоб не перезаписывается

#### Scenario: Удаление одного из треков
- **WHEN** удаляется трек, делящий блоб с другим треком
- **THEN** блоб сохраняется
- **AND** удаляется только ссылка

### Requirement: Двухфазная запись и GC

Hub SHALL записывать объект в S3 и фиксировать его в БД двухфазно: объект получает статус `pending`, затем `committed` после успешного коммита метаданных. Осиротевшие `pending`-объекты и блобы без ссылок MUST удаляться фоновой задачей.

#### Scenario: Успешный импорт
- **WHEN** объект загружен и метаданные закоммичены
- **THEN** блоб переходит в `committed`
- **AND** становится доступен для выдачи

#### Scenario: Сбой после загрузки объекта
- **WHEN** коммит метаданных не удался
- **THEN** объект остаётся `pending`
- **AND** повторная попытка идемпотентна по `sha256`

#### Scenario: GC осиротевших блобов
- **WHEN** блоб не имеет ссылок дольше установленного срока
- **THEN** фоновая задача удаляет объект
- **AND** пишет результат в лог

### Requirement: Горячий кэш

Hub SHALL кэшировать байты на локальном диске для стриминга, ffprobe/ffmpeg и embedder. Кэш MUST иметь лимит размера и вытеснение по давности использования.

#### Scenario: Повторное прослушивание
- **WHEN** трек запрашивается второй раз
- **THEN** байты читаются из локального кэша без обращения к S3

#### Scenario: Переполнение кэша
- **WHEN** размер кэша превышает лимит
- **THEN** Hub удаляет записи, которые дольше всего не использовались

### Requirement: Метаданные объекта для восстановления

При импорте Hub SHALL записывать в S3 user-metadata минимум (`sha256`, `uid`, `artist`, `title`, `album`) и MUST сохранять manifest **на каждый трек** — `manifests/<sha256>/<uid>.json`, потому что один блоб может обслуживать несколько треков. Это MUST позволять частичное восстановление каталога при потере БД.

#### Scenario: Потеря БД
- **WHEN** БД утрачена, а бакет сохранён
- **THEN** по manifest и user-metadata можно восстановить базовые метаданные треков

#### Scenario: Делимый блоб
- **WHEN** два трека ссылаются на один `sha256`
- **THEN** у каждого свой `manifests/<sha256>/<uid>.json`
- **AND** восстановление даёт оба трека

#### Scenario: Правка метаданных
- **WHEN** метаданные трека изменены в БД
- **THEN** manifest MAY обновляться фоновой задачей
- **AND** отсутствие обновления не блокирует работу

### Requirement: Ёмкость и health хранилища

Hub SHALL сообщать администратору состояние S3: доступность бакета, объём библиотеки и занятость локального кэша. Оценка свободного места MUST NOT блокировать операции.

#### Scenario: Health S3
- **WHEN** администратор запрашивает расширенный health
- **THEN** Hub возвращает статус S3 и объём кэша

#### Scenario: Квота бакета
- **WHEN** бакет близок к квоте
- **THEN** Hub сообщает предупреждение
- **AND** не блокирует импорт автоматически

### Requirement: Доступ к блобу для embedder

Hub SHALL предоставлять endpoint `/api/media/blob/<sha256>`, защищённый `MEDIA_BLOB_TOKEN` (`Authorization: Bearer`, constant-time compare), для чтения блоба, когда presigned URL недоступен. Endpoint MUST поддерживать `Range` и MUST NOT требовать пользовательской cookie.

#### Scenario: Embedder без presign
- **WHEN** embedder запрашивает блоб по `/api/media/blob/<sha256>` с сервисным токеном
- **THEN** Hub отдаёт байты из кэша или S3
- **AND** поддерживает `Range`

#### Scenario: Нет токена
- **WHEN** запрос приходит без `MEDIA_BLOB_TOKEN`
- **THEN** Hub возвращает `401`

#### Scenario: Объект вне БД
- **WHEN** объект в префиксе `audio/` отсутствует в `blobs` дольше TTL
- **THEN** GC удаляет его
- **AND** не трогает объекты со ссылками

#### Scenario: Коммит блоба
- **WHEN** объект скопирован в `audio/<sha256>` и проверен `head`
- **THEN** строка блоба и строка трека коммитятся в одной транзакции
